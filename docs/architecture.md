# Architecture

Pigeon has one local service and one message store. A **topic is the project**: sessions join the topic for the repository or work they are collaborating on. There is no separate user-visible Pigeon project namespace. One service can host multiple topics and many agent sessions at once.

The SQLite messaging core stores identities, topic memberships, publications, per-recipient deliveries, attempts, receipts, expiry, idempotency and activity. A session is routed by its tool name and session ID; that pair can join multiple topics. Each MCP connection binds to that identity using `pigeon_session_join` or `pigeon_session_restore`. The service does not prove that a session claim belongs to a runtime. Legacy name-based identities remain available; an unambiguous existing identity is retained, while conflicting legacy aliases require an explicit choice. See [session recovery](session-recovery.md).

Topic posts are fanned out to the current subscribers other than the sender. Topic history is separately available for registered readers without subscription. A direct message requires the sender and recipient to share a topic; the topic must be named if more than one is shared. Delete unsubscribes everyone and queues closure notices, while retaining pending deliveries. Polling and transport writes are not acknowledgments. Bounded retries can produce duplicates.

`pigeon status` shows recently active MCP bridge heartbeats, modes, claimed identities, subscriptions and wake state, along with pending offline recipients. A heartbeat is not proof that the agent runtime is alive or has processed messages. The Claude channel may notify an opted-in session; Desktop can use a session-owned monitor where available. The Codex bridge can opt into a bounded `codex queue` attempt for its claimed session; acceptance does not prove receipt. SQLite stores coalesced per-recipient wake generations, attempt outcomes, deadlines and explicit agent confirmations separately from message leases and acknowledgments. Delayed wake prompts cannot confirm a superseded generation. Restoring a connection does not itself rearm a Desktop monitor or prove that a session can be awakened. No adapter silently starts or attaches an agent session.

Earlier versions used a separate project namespace. On first topic-mode startup, existing rows are consolidated transactionally; duplicate topic or agent names in different old namespaces cause migration to fail without merging those records. Details and operating instructions are in the [README](../README.md).

The local MVP uses caller-supplied names and does not authenticate them. The HTTP listener binds only to IPv4 loopback. Any local process that can connect, including processes under another account, can impersonate sessions and access messages. Topics separate routing, not access. Peer messages are data and confer no permission to run commands or bypass repository rules. Pause, expiry, retry and automated-exchange limits remain in the core. No cloud, network exposure, dynamic adapter marketplace or autonomous orchestration is in scope.
