# Pigeon session wake research

Research date: 2026-10-30. This is a design and evidence report, not a claim that the proposed changes are implemented. Scope: existing Codex and Claude sessions on one machine. No credentials, restricted session stores, global configuration, or Sigma sessions were inspected for this research.

## Finding

Pigeon can durably retain an inbox independently of wake delivery. It cannot guarantee that a closed, blocked, disconnected or non-cooperative agent will wake or acknowledge a message. A credible contract is conditional: while a supported session and its wake path are available, retry bounded wake requests and expose whether the agent explicitly confirmed receipt; otherwise retain the message until its expiry and clearly report the degraded state. Do not claim exactly-once processing.

## Runtime capabilities

### Codex

* [Codex queue](https://learn.chatgpt.com/docs/developer-commands) sends text to an existing session by UUID or name. The installed CLI reports that queued messages use the thread's model; `--resume` attempts to resume a thread and can still exit successfully after a failed resume. Pigeon currently does not use `--resume`.
* Our isolated idle test observed Pigeon's fixed wake arrive in an app-server-owned thread. In our current desktop-chat test, the user confirmed a queued wake was delivered automatically after the prior turn; Claude also acknowledged our message. Multiple old wake prompts then produced empty-inbox turns after we had polled early. This demonstrates one path in a specific configuration, not every app, session state or restart.
* [App-server](https://learn.chatgpt.com/docs/app-server) offers `turn/steer` for an active turn with the expected turn ID and `turn/start` for starting generation. It also offers `thread/inject_items`, which adds context but explicitly does not start a turn. A client needs a supported connection to the owning server; starting a separate server or resuming a thread there must not be misrepresented as injecting into the already-running desktop conversation. The app-server command is [experimental and not supported for production workloads](https://learn.chatgpt.com/docs/mcp-server).
* Codex's app exposes a thread-bound heartbeat automation, which can invoke an inbox check on a schedule. This is polling that runs the agent and may consume model usage. It is not a documented silent delivery channel or proof that an independently running Pigeon process can invoke the app's internal tools. A separate scheduled task with a cheaper model is a separate task and does not automatically inject a message into the existing chat.
* Codex app tools available inside an authorized agent include a send-message-to-thread action. Its prompt is user-visible and it is an agent tool, not an established standalone interface Pigeon can call from its service. Do not build on that assumption without a supported contract and test.

### Claude Code and Desktop

* [Claude Channels](https://code.claude.com/docs/en/channels-reference) can push to an opted-in running Claude Code session. While the agent is busy, events queue for a later turn. Anthropic states that a transport write is not acknowledged by Claude and events may be silently dropped when the server is not loaded as a channel or policy blocks it. Events arrive only while the session is open.
* Our isolated HTTP test of an interactive Claude Code session observed the channel event, the agent's explicit acknowledgment and the matching database state. One startup warning said the server was not configured even though the server later connected and delivered the event; a banner or a bridge capability alone is not an end-to-end probe.
* Custom channels are in research preview and require the [development flag and interactive confirmation](https://code.claude.com/docs/en/channels-reference). The user's Claude Desktop session cannot use that flag in the observed workflow. Anthropic's [desktop flag comparison](https://code.claude.com/docs/en/desktop) says unlisted CLI flags have no desktop equivalent; it does not list the development-channel flag. Do not assume that an MCP bridge reporting `claude-channel` means Desktop is accepting channel events. An official allowlisting or future desktop option is a vendor-dependent path, not a current Pigeon feature.
* Claude Code documents a [session-scoped scheduler](https://code.claude.com/docs/en/scheduled-tasks) as an event-independent polling fallback, with a one-minute minimum, idle-only execution, jitter, and seven-day recurring-task expiry. Scheduled prompts use the agent; they are not free lightweight service checks. Whether the specific Desktop session and the user's currently configured external scheduler have the same semantics is unverified.

## Current implementation gaps

* A bridge heartbeat reports process activity and claimed mode, not whether its host accepts wake notifications, whether the agent is running, or whether the right session owns the claim.
* `CodexQueueNotifier` polls every 500 ms within the MCP bridge. A zero exit code suppresses further attempts for that message during the bridge lifetime, even if no agent reads it; failures are tried at most three times with in-memory state. A restart loses this state. It generates one visible queued prompt per message and cannot retract one already submitted through the documented CLI.
* `ClaudeChannel` records successful transport writes but holds its notified IDs in a process-local set, does not observe runtime receipt, and can emit again after bridge restart. Both notifier sets stop adding entries after 1,024 distinct message IDs until the bridge restarts. Neither behavior establishes reliable wake delivery.
* A restarted MCP bridge starts unregistered. Pigeon does not establish automatically which runtime session owns it. Subscriptions and messages survive, but a live bridge must re-associate with the correct identity before it can notify. Caller-supplied routing identities are unauthenticated in this MVP.
* Current message leases expire after 30 seconds and the default delivery-attempt limit is three. A slow agent or repeated polling without acknowledgment can exhaust attempts. Wake retries must be tracked separately from delivery attempts and must not lease a message just to detect pending work.

## Recommended design

1. Keep the SQLite message store and per-recipient acknowledgments as the source of truth. The core emits a durable inbox-needs-attention signal when a recipient transitions to having pending unacknowledged work. Per recipient and session, track a persistent wake generation, attempt time, outcome, retry deadline and explicit confirmation. Retain explicit expiry and bounded backoff; do not infer processed state from a process exit code, heartbeat, or transport write.
2. Coalesce a burst into at most one outstanding wake per session rather than one per message. A single wake tells the agent to drain a bounded inbox batch and acknowledge each message. If new messages arrive while a wake is outstanding, they are covered by the same wake where possible. Recheck the inbox after processing to close the race with new arrivals. Already submitted Codex user prompts may still be visible and cannot be assumed retractable. A generation token can make old wakes cheap no-ops when they eventually run; it cannot suppress a turn already queued in the host.
3. Separate **bridge connected**, **notification configured**, **transport accepted**, **agent confirmed**, and **delivery acknowledged** in status. A bounded challenge delivered only through the actual notification channel and explicitly confirmed through the same bridge can demonstrate the path for that session at that time. Such a challenge is not authentication or a guarantee of future liveness; caller-supplied session claims can be impersonated. If unconfirmed, mark wake support unverified/degraded, retain messages, and provide the user with a clear setup or polling choice.
4. Codex default: continue the documented queue path when its target is actually reachable, with per-session coalescing, durable tracking and explicit consumption confirmation. Accept the visible queued prompt as a product limitation for now. Investigate an app-server event-driven integration only for a session whose owning server is intentionally available; handle idle/active races and never silently steer or resume another session. A periodic heartbeat is an opt-in fallback, not the default for every message or a cheaper model substitute.
5. Claude Code with verified channel: continue using channel notifications, but confirm via an agent-level challenge and acknowledge messages explicitly. For Claude Desktop where channel activation is unavailable, show notifications as unavailable instead of pretending that an MCP connection is a channel. Offer the existing user-approved scheduler/polling as an explicit degraded fallback, and investigate a documented native Desktop channel enablement path or official allowlisting with Anthropic. Do not rely on hidden desktop internals, simulated UI input, external messaging services, or alternate agent processes as a substitute for the existing session.
6. Session identity and registration need an explicit rebind strategy. Keep durable identity/subscription separate from a live bridge connection, expose why a rebind is required, and use runtime-provided identifiers where documented. Do not read session stores or guess a session ID. Test how each runtime passes its actual session ID to MCP; only automate rebind once the source and ownership are verified.

## Proposed experiments

All real-runtime experiments require explicit approval for new test sessions and must use synthetic content, disposable storage and no global configuration changes. First test coalescing and persistent state using mock runtimes and a fake clock. Then, for each supported real surface, record separate timestamps for stored, wake attempted, transport accepted, agent challenge-confirmed, message received and acknowledged. Cover idle, busy, bridge restart, service restart, temporary disconnect, host session closed, notification disabled, silently dropped channel, duplicate notification, burst messages, slow processing past a lease, and deliberate crash between write and acknowledgment. Observe retries and bounded limits, no self-notification, no new agent session and no permission bypass. Test Claude Desktop and Codex Desktop explicitly rather than inferring their behavior from terminal-owned sessions. Stop and report the case where the host has no supported wake mechanism.
