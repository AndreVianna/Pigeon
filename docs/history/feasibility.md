## Installed surfaces

It says `--resume` attempts to resume on the local daemon or selected remote server and that a failed resume is only a warning, while the command still succeeds. The installed CLI also generated an experimental app-server schema containing `thread/queue/add` with a client message ID, input and thread ID. These are available command/schema surfaces, not proof of delivery or of which app-owned sessions they can reach. The commands emitted a home-directory warning under this sandbox.

## Delivery findings

| State | Codex | Claude Code Channels |
| --- | --- | --- |
| Idle, open | A user-run isolated probe observed `thread/queue/add` acceptance, a user-input event and an agent acknowledgment in a newly created thread owned by that app-server. The installed `codex queue` CLI and reachability of separately owned sessions remain untested. The [app-server API](https://learn.chatgpt.com/docs/app-server) can also resume a thread and start a turn on a server that owns or loads it. | In a user-run isolated interactive session, the fixture recorded a channel transport write and matching agent acknowledgment; the user shared the agent's confirmation. The registration notice and channel-input event were not separately reported. [Channels](https://code.claude.com/docs/en/channels) are a research preview. |
| Busy | In a separate user-run test, queue acceptance was observed before the initial turn's completion, followed by a queued user-input event and a matching agent reply. The test did not record whether dispatch occurred after completion, and the CLI queue remains untested. [Codex queue and steer](https://developers.openai.com/blog/mastering-codex-remote-for-engineering) are different: the product queue waits for a later turn; `turn/steer` targets the active turn. | The [channel reference](https://code.claude.com/docs/en/channels-reference) says events queue while busy and are processed together on a later turn. |
| Closed or restart | A user-run probe created a new thread, restarted its owned app-server, resumed that same thread, then observed queue acceptance, input and a matching agent reply. It did not submit or preserve a queue item while the server was offline. `queue --resume` and attachment to an independently owned desktop session remain untested. | Events arrive only while the session is open. The channel must be loaded again after restart; Pigeon must retain and redeliver offline messages itself. |

`stored` means Pigeon committed a message. `polled` means an adapter or mock acquired a lease; neither proves that a model saw it. Runtime acceptance also does not prove agent action. Claude explicitly documents that notification transport completion is not a processing acknowledgment and that blocked or unloaded channels may silently drop events. An explicit agent reply or acknowledgment tool call is needed for agent-level evidence. Codex queue command success likewise does not prove a reply; observe the target session and request a correlated acknowledgment.

Custom Claude channels are a [research preview](https://code.claude.com/docs/en/channels-reference): custom entries require the development flag in an interactive session, a confirmation, and account/organization eligibility. Non-interactive `-p` ignores the development bypass. A channel is a session-spawned stdio MCP subprocess; do not mistake another Claude process launched with `--resume` for delivery into the already-running session. No permission relay is needed or proposed.

## Smallest proposed architecture

The original recommendation was an authenticated local host; this was superseded by the user's explicit no-authentication MVP direction. The current host uses caller-supplied project and identity labels over a local named pipe, with the limits described in [local trust and operational boundaries](../security-design.md). Topic subscriptions and direct recipients are explicit, and notification does not replace durable storage. See [architecture direction](../architecture.md) for current implementation boundaries.

The earlier synthetic-grant implementation and its tests are historical; it is no longer the current protocol. A same-user ACL cannot distinguish processes running under the same Windows account.

## Proposed isolated test; approval required before execution

Use only a new disposable test directory and two newly created sessions, with known IDs captured at creation and synthetic messages. Never discover or touch existing project sessions. Limit each test to one ping and one reply plus at most one controlled retry. Keep normal permissions and network boundaries; no global config, permanent credentials, firewall changes, service installation, or persistent daemon. Stop on unexpected prompts, inaccessible account/channel policy, ambiguous session ownership, or an inability to verify the target.

1. **Codex:** create a disposable session under the test directory and record its own ID. In the owning app-server/client, wait for an idle checkpoint. Submit a unique `PIGEON_TEST_<nonce>` using the installed queue interface targeting exactly that ID. Record command result separately from the target's visible receipt and its explicit matching reply. If supported, repeat once while a bounded turn is busy and confirm that it is handled after that turn; do not use steering. Exit and resume the same saved test thread once and independently observe a queued test marker. A separate app-server loading the same history is not evidence of delivery to the original running process.
2. **Claude:** prepare a minimal project-local channel fixture and verify its dependencies without changing global configuration. With approval, launch an interactive disposable session with the documented development channel flag and normal permissions; explicitly accept its development warning only for this fixture. Record the actual session identity and channel registration. Send one unique synthetic event through that session's channel and require the agent to call a fixture reply/ack tool with the same nonce. Record transport write, visible receipt, and agent acknowledgment separately. Test a busy turn only if a deterministic bounded checkpoint is available; stop and restart the same session and show that Pigeon's durable queue, rather than Channels alone, supplies any offline message.
3. If either live route is unavailable, record the exact condition and use the explicit polling path at a safe checkpoint. The current mock CLI demonstrates only Pigeon's polling mechanics, not integration with an agent.

For a narrower first step, the default mode of `experiments/codex_queue_probe.py` prepares a single owned app-server over stdio, creates one test thread, waits for an initial turn, and submits one idle experimental queue message. It records RPC acceptance, whether a user-message event was observed, and a matching agent response separately. It terminates its own app-server and does not enumerate existing threads or start a local daemon. The default mode does not test busy or restart delivery.

The probe also has a `--busy` option. It creates a new isolated test thread, starts one bounded turn, and queues one synthetic marker after observing that turn start. It reports whether queue acceptance was observed before the initial turn completed, then checks for the matching response. A race where the first turn finishes too soon is inconclusive, not a busy-delivery success. The user ran this option in their normal PowerShell and reported acceptance before completion, followed by observed input and a matching response. Its output did not establish dispatch ordering relative to the first turn's completion. Restart behavior still needs its own experiment.

`experiments/codex_restart_probe.py` creates one new test thread, completes a seed turn, stops its own app-server, starts another app-server, resumes only that known test thread, then submits and observes one synthetic queue message. The user ran it and reported that the same thread resumed, the queue RPC accepted the marker, a matching input event was observed, and the agent replied with the acknowledgment marker. It tests delivery after resume, not survival of a queue item submitted while the server was offline.

### Probe result: 2026-10-29

With approval, sandboxed attempts exited before initialization; sanitized diagnostics reported `home directory` and `startup error`. A user-run attempt initially failed because Codex was absent from that shell's PATH; the probe was updated to find the app installation without changing PATH. On a subsequent run in the user's PowerShell, the user reported: one isolated thread created; initial turn completed; queue RPC accepted; the queued user-input event was observed; and the agent response contained the matching acknowledgment marker. This establishes idle delivery for that newly created, probe-owned app-server thread. A separate user-run busy test reported acceptance before the first turn completed and a later matching response, but did not measure dispatch ordering. A third probe established delivery after restarting the owning app-server and resuming its new test thread. These tests do not establish attachment to a separate already-running desktop session. The assistant did not independently observe the sessions, and the probes did not enumerate or target existing sessions.

### Pigeon end-to-end polling test: 2026-10-29

With explicit approval, `experiments/polling_e2e.py` ran outside the sandbox using a temporary database, synthetic grants, an ephemeral Codex app-server thread and a new nonpersistent Claude Code session. Each agent registered its own test identity through its Pigeon MCP bridge. Codex sent one synthetic ping; the database showed it queued before Claude polled and acknowledged it. Claude sent a reply linked to the ping, and Codex polled and acknowledged that reply. The database showed an acknowledged attempt for each delivery. All steps used the same disposable Pigeon service; no notification adapter or push was involved.

Codex required confirmation for the test MCP calls. The harness accepted only the explicitly expected Pigeon tool in each test phase; unexpected approval or input requests stop the test. An earlier attempt timed out before a ping was sent, and a subsequent diagnostic attempt identified the confirmation request. The successful exchange then exited with a cleanup error because the temporary SQLite database was still open. The harness now explicitly closes its read-only verification connections; a separate synthetic database cleanup check passed, and the original temporary test directory was removed. The complete agent exchange has not been repeated since that cleanup fix.

This verifies polling between those newly created test sessions. It does not verify delivery into separately owned existing sessions, busy-session notification, offline delivery across a service restart with real agents, mailbox fan-out between real agents, or production security and credential provisioning.

### Preconfigured running-session polling test: 2026-10-30

With explicit approval, the `--already-running` mode started a new ephemeral Codex thread and a new nonpersistent Claude Code session, each with the synthetic Pigeon MCP bridge configured from startup. Each session completed an initial turn and remained running before the disposable Pigeon service started. Both then registered, Codex stored a ping, Claude polled and acknowledged it and sent a correlated reply, and Codex polled and acknowledged the reply. The harness inspected the disposable database for the expected attempts, shut down the test processes, cleaned up its temporary directory, and exited successfully. No existing project session or global configuration was targeted.

This establishes polling in sessions that were already running when the Pigeon service started, **provided that their MCP bridge had been configured at session startup**. It does not establish adding Pigeon to an already-running, previously unconfigured session or automatic notification. This later successful run also exercised the prior temporary-database cleanup fix.

## Remaining before real use

Further work includes testing the current polling workflow with both real agents, Codex notification integration, busy and restart cases, and additional concurrency and crash recovery checks. Hooks are a possible later enhancement, not an existing delivery guarantee.
